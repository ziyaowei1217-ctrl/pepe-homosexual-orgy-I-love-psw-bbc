# 渐进式邮箱登录与新用户引导设计

## 目标

在保留现有无密码邮箱验证码认证的基础上，把当前单行“登录 / 注册”表单升级为清晰、可靠的分步流程，并为首次注册用户提供可跳过的资料引导。普通浏览不受资料完整度限制；发布房源等依赖身份信息的关键操作会要求用户先补全必要资料。

## 范围

本次包含：

- 分步邮箱验证码登录与自动注册；
- 首次注册用户识别；
- 验证码重发倒计时、修改邮箱、输入状态和错误反馈；
- 首次登录后的可跳过资料引导；
- 资料完整度判断与关键操作前拦截；
- 会话恢复、失效清理和退出反馈；
- 前端、API 与浏览器回归测试。

本次不包含：

- 密码登录；
- 第三方 OAuth；
- 手机验证码；
- 找回密码；
- 生产邮件供应商配置；
- 多设备会话管理。

## 用户体验

### 登录与注册

账户面板使用三个明确状态：

1. `email`：用户输入邮箱并请求验证码。
2. `code`：界面显示验证码已发送到哪个邮箱，提供六位验证码输入、修改邮箱和重发入口。
3. `authenticated`：展示当前账户、资料状态、资料编辑和退出入口。

请求成功后进入验证码状态。开发环境可以继续自动填入 API 返回的 `devCode`，但界面用“本地开发验证码”明确标记，避免与生产体验混淆。

验证码状态包含：

- 六位数字输入约束；
- 提交中的禁用状态；
- 60 秒重发倒计时；
- 到期时间说明；
- “修改邮箱”返回上一步；
- 错误发生时保留邮箱和验证码输入；
- 登录成功后清空临时验证码状态。

### 新用户引导

API 在验证码验证成功后返回 `isNewUser`。首次创建用户时为 `true`，已有用户登录时为 `false`。

新用户登录成功后打开资料引导，收集：

- 显示名称；
- 身份：租客、房东、租客兼房东；
- 学校；
- 城市。

用户可以跳过。跳过后仍可浏览房源、查看室友和使用不依赖身份资料的功能。账户入口持续显示“资料待完善”状态。

微信、Instagram 和个人简介不放在首次引导中，仍保留在完整资料编辑区域。

### 关键操作拦截

资料完整条件为：

- `displayName` 非空；
- `role` 是 `renter`、`lister` 或 `both`；
- `school` 非空；
- `city` 非空。

普通浏览不拦截。进入房东发布流程时：

1. 未登录：打开登录面板并说明“登录后继续发布”；
2. 已登录但资料不完整：打开资料引导并说明缺少哪些字段；
3. 资料完整但身份不是 `lister` 或 `both`：引导用户修改身份；
4. 条件满足：继续原来的发布流程。

本次只为发布房源设置强制门槛，避免把未经确认的规则扩散到消息、看房或室友操作。

## 前端结构

### 纯逻辑模块

新增 `lib/auth-flow.ts`，集中管理可测试的认证与引导规则：

- 邮箱规范化与基础校验；
- 验证码数字规范化；
- 登录流程状态；
- 资料完整度与缺失字段；
- 登录后是否打开引导；
- 发布房源前的下一步判断。

React 组件只负责渲染和调用这些规则，避免继续把认证判断堆进大型 `components/sublet-app.tsx`。

### 组件边界

新增 `components/auth-flow-panel.tsx`，负责：

- 邮箱和验证码两个未登录步骤；
- 倒计时；
- 请求、验证和错误展示；
- 已登录账户摘要；
- 触发资料引导与退出。

新增 `components/profile-onboarding.tsx`，负责：

- 四个首次引导字段；
- 缺失字段提示；
- 保存、稍后完善和返回资料编辑；
- 保存成功后的完成状态。

`components/sublet-app.tsx` 保留全局认证状态、资料请求、路由意图和 toast，但不再包含登录表单的内部状态机。

## API 与数据流

### 请求验证码

继续使用：

```text
POST /api/v1/auth/email-code
```

响应保留：

- `email`；
- `expiresAt`；
- 非生产环境下的 `devCode`。

前端使用服务端 `expiresAt` 显示有效期，重发倒计时固定为 60 秒，与当前后端冷却时间一致。

### 验证验证码

继续使用：

```text
POST /api/v1/auth/verify-email
```

响应扩展为：

- `accessToken`；
- `user`；
- `isNewUser`。

后端在 `user.upsert` 之前查询邮箱是否已有用户，或改用能可靠区分创建与更新的事务流程。用户、Profile 和验证码消费必须保持现有一致性：验证码验证失败不创建用户，验证成功才创建或恢复会话。

### 会话恢复

页面启动时继续从版本化本地会话读取访问令牌，然后调用 `/auth/me` 和 `/profiles/me`。任一认证请求返回 401 时：

- 清除本地令牌；
- 清空内存中的用户与资料；
- 显示“登录状态已失效，请重新登录”；
- 保留当前路由，避免把用户无故送回首页。

## 错误处理

界面直接在相关步骤附近显示错误，同时保留全局 toast：

- 邮箱格式错误：停留在邮箱步骤；
- 冷却期内重发：保留验证码步骤和倒计时；
- 验证码格式错误：不发送请求；
- 验证码错误或过期：保留邮箱，允许重新输入或重发；
- 网络或 API 不可用：不伪造成功状态；
- 资料保存失败：保留用户输入，不关闭引导；
- 会话失效：清理本地认证状态并允许重新登录。

错误文案使用中文用户语言，不直接展示 NestJS 或数据库内部错误。

## 可访问性与响应式

- 邮箱、验证码和资料字段都有可访问标签；
- 错误区域使用 `role="alert"`；
- 当前步骤使用可读文字，不只依赖颜色；
- 验证码输入支持数字键盘提示；
- 所有按钮在请求期间禁用并显示动作中的文案；
- 桌面端为并排账户面板，移动端为单列步骤；
- 首次引导使用页面内面板，不使用阻塞浏览器原生对话框。

## 测试策略

### 前端单元测试

覆盖：

- 邮箱与验证码规范化；
- 登录步骤转换；
- 重发状态；
- 新用户与已有用户的引导判断；
- 资料完整与缺失字段；
- 发布房源前的登录、资料和身份门槛；
- 会话失效后的清理。

### API 测试

覆盖：

- 首次验证码验证返回 `isNewUser: true`；
- 已有用户再次登录返回 `isNewUser: false`；
- 管理员识别不受影响；
- 错误、过期和尝试次数限制不创建新用户；
- 成功验证仍创建 Profile 并消费验证码。

### 浏览器验证

使用本地 PostgreSQL 和开发验证码完成：

1. 新邮箱请求验证码；
2. 验证并进入首次资料引导；
3. 跳过后继续浏览；
4. 再次打开发布入口时被引导补全资料；
5. 保存资料并进入发布流程；
6. 退出；
7. 使用同一邮箱再次登录，确认不再显示首次引导；
8. 刷新页面确认会话恢复；
9. 检查浏览器控制台无错误。

## 成功标准

- 用户能理解自己处于输入邮箱、输入验证码或已登录的哪一步；
- 首次邮箱验证与已有用户登录在 API 层可区分；
- 新用户可以跳过资料引导并继续普通浏览；
- 发布房源前会准确要求登录、完整资料和房东身份；
- 验证失败、重发、网络失败和会话失效均不会伪造成功；
- 完整前端检查、API launch check 和真实数据库浏览器流程通过。
