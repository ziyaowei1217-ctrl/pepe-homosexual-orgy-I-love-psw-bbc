# 邀请制内测生产化设计

日期：2026-08-03

## 1. 目标与范围

本轮把现有本地 MVP 升级为可控放量、可审核、可恢复的邀请制内测系统。默认生产架构为 Vercel 前端、Render API/PostgreSQL/Valkey（Oregon）、Cloudflare R2 图片与异地备份、Resend 邮件、Sentry 错误监控和 Better Stack 日志与告警。

工作拆成三个依次交付、可独立验收的单元：

1. 认证与管理员安全；
2. 图片发布与人工审核；
3. 生产部署、监控、备份与恢复演练。

预计工程工期为 12–17 个工作日。域名验证、服务商审核和外部资源开通另预留 1–3 个自然日。

本轮不包含支付、自动 AI 图片审核、公开邀请码管理页面、室友匹配重构或其他新业务模块。

## 2. 决策与备选方案

采用分三批生产化方案。它比“一次性全量上线”更容易隔离认证、媒体和部署风险，也比“仅部署当前 MVP”更符合真实用户数据和房源图片的安全要求。第三种备选是把 API 与前端统一迁到单一平台，但会扩大现有 NestJS/Prisma 架构的迁移面，且不能明显降低本轮风险，因此不采用。

每批必须满足自己的自动化测试和人工验收门槛后才能进入下一批；数据库迁移始终遵循 expand/contract，不修改已有迁移文件。

## 3. 当前基线与主要缺口

现有代码已具备 Next.js 前端、NestJS API、Prisma/PostgreSQL、邮件验证码登录、管理员角色、房源提交与审核、消息和室友匹配。关键缺口包括：

- 生产邮件发送器尚未接入，生产环境当前会在发送时失败而不是启动时失败；
- 验证码仍使用现有哈希方案，邮件发送发生在数据库事务内，且没有分布式限流和投递状态；
- `LOCAL_ADMIN_EMAILS` 仍可在登录时自动提权；
- 存在旧 `HousingListing` 数据模型和当前 `Listing` 模型的双轨结构；
- `Listing.image` 必填，`ListingMedia` 仅保存任意 URL，没有私有上传、处理和发布状态；
- 缺少生产部署声明、发布审批、结构化脱敏日志、外部监控及可执行恢复手册。

## 4. 第一批：认证与管理员安全

### 4.1 生产邮件

实现 Resend 邮件发送器，使用已验证发信子域名、SPF/DKIM 和独立 API Key。开发环境继续使用控制台发送器；生产环境必须在应用启动阶段校验 Resend API Key、发件人和已选择的发送器，缺失或仍为控制台配置时拒绝启动。

邮件发送器返回服务商消息 ID，并使用结构化错误类型区分可重试与不可重试失败。任何日志都不得包含验证码、完整邮箱或邮件正文。

### 4.2 验证码生命周期

验证码保持 6 位、10 分钟有效、最多尝试 5 次、60 秒发送冷却。每条记录使用随机盐和带服务端密钥的 HMAC-SHA256，保存哈希版本以支持后续轮换。

`VerificationCode` 增加：

- `purpose`：登录、管理员二次验证等用途；
- `salt`、`hashVersion`；
- `deliveryStatus`：`PENDING`、`SENT`、`FAILED`；
- `providerMessageId`、`sentAt`、`failedAt`；
- 现有过期、消费和尝试次数字段继续保留。

请求验证码时，在短事务中获取邮箱级数据库锁、检查冷却并创建 `PENDING` 记录，然后提交事务。邮件在事务外发送。发送成功后把新记录标为 `SENT`，并在短事务中使该邮箱同用途的旧验证码失效。发送失败则把新记录标为 `FAILED`，不使上一条仍有效的 `SENT` 验证码失效，并返回统一的 `AUTH_DELIVERY_UNAVAILABLE`。

验证只查询指定用途下最新、未消费、未过期且状态为 `SENT` 的记录。部署新增字段时，显式使所有旧的未消费验证码失效，不影响用户和会话数据。

### 4.3 分布式限流和设备标识

前端首次访问时生成高熵匿名 `X-Device-ID`，持久化在浏览器本地存储；所有验证码发送和验证请求都携带该标识。后端只在明确配置的受信代理链后读取转发 IP，其他情况使用直接连接地址。

使用 Render Valkey 以固定窗口或滑动窗口计数器实现以下限制：

- 发送：邮箱 5 次/小时、10 次/天；设备 10 次/小时；IP 30 次/小时；全站 100 次/分钟；
- 验证：邮箱 15 次/15 分钟；设备 30 次/15 分钟；IP 100 次/15 分钟；全站 300 次/分钟。

任一维度超限即返回 `429`、正确的 `Retry-After` 和稳定错误码 `AUTH_RATE_LIMITED`。生产环境 Valkey 不可用时，验证码发送与验证均失败关闭；健康检查应把依赖故障反映到 `/ready`，而 `/health` 仅表示进程存活。

### 4.4 邀请制

新增 `BetaInvite`，至少保存规范化邮箱、状态、邀请人、创建/使用/撤销时间和审计关联。只有有效且未撤销的邀请邮箱可以完成新用户注册；已注册用户继续允许登录。

邀请名单只通过服务器运维命令管理，不提供公共或管理员 HTTP 管理接口。命令必须幂等，并支持新增、查看和撤销；输出中邮箱必须脱敏。

### 4.5 管理员提权、二次验证和审计

生产环境禁止 `LOCAL_ADMIN_EMAILS` 自动提权。管理员授予与撤销仅允许通过服务器命令完成，命令必须记录操作者、原因和目标用户，并拒绝撤销最后一名管理员。

管理员写操作要求 JWT 中带有最近 30 分钟内完成的管理员二次邮件验证声明。过期或缺失时返回 `ADMIN_REAUTH_REQUIRED`；读取操作仍按现有管理员角色控制。信任队列的写操作迁到同一管理员安全边界。

新增不可由应用更新或删除的 `AuditEvent`。事件至少记录事件类型、操作者、目标、原因、请求 ID、时间、成功或拦截结果及安全所需的最小元数据。提权、撤权、审核、拒绝、下架及被二次验证拦截的管理员操作必须写入审计事件。数据库角色或触发器阻止应用层修改和删除历史事件。

## 5. 第二批：房源接口、真实图片与审核

### 5.1 退役旧房源接口

`/api/v1/housing-listings` 的所有 HTTP 方法统一返回 `410` 和 `LEGACY_LISTINGS_RETIRED`，响应指向 `/api/v1/listings`。删除旧业务写路径，但保留旧数据表为只读归档。本轮不删除该表或其当前数据。

数据库增加写保护，使应用数据库角色无法对旧表执行 INSERT、UPDATE 或 DELETE；迁移和恢复所用高权限角色不受该限制。验收需要证明应用层无法绕过保护。

### 5.2 媒体状态模型

关闭 `POST /listings/:id/media {url}`，并从房源输入 DTO 删除任意外部图片 URL。已有记录的展示 URL只做兼容读取，不能成为新写入路径。

`Listing.image` 改为可空并只由服务端维护。`ListingMedia` 增加：

- 私有原始对象键、私有处理后对象键、公开对象键和公开 URL；
- 上传、处理、审核、发布状态；
- 声明 MIME、探测 MIME、字节数、宽高、校验值；
- 排序、失败原因、审核人、审核时间和发布时间。

`ListingStatus` 增加 `SUSPENDED`；公开列表和详情仍只返回 `APPROVED`，且仅暴露已经发布的公开媒体 URL。

### 5.3 存储与上传协议

R2 使用三个逻辑隔离的桶：私有暂存桶、公开成品桶、独立私有备份桶。后端生成不可预测且包含所有权范围的对象键，绝不接受客户端对象路径。

新增接口：

- `POST /listings/:id/media/uploads`：校验所有权、数量和声明元数据，创建媒体记录并返回 5 分钟有效的预签名 PUT；
- `POST /listings/:id/media/:mediaId/finalize`：幂等确认对象存在、大小和校验信息后进入处理；
- `DELETE /listings/:id/media/:mediaId`：删除草稿媒体及其私有对象；已发布媒体走安全下架流程；
- `PATCH /listings/:id/media/order`：原子更新同一房源媒体排序。

预签名 URL 视为短期 bearer token。签名绑定对象键和 Content-Type，R2 CORS 仅允许受信前端域名。由于同一预签名 PUT 在过期前可能重复使用，`finalize` 必须幂等，并以服务端读取到的对象元数据和校验结果为准。

### 5.4 文件处理与安全校验

只接受 JPEG、PNG、WebP；单张最大 8 MiB，每套房最多 12 张。拒绝 SVG、GIF、HEIC、伪造 MIME、超过 40MP 或任一边超过 12000px 的文件。

后端工作进程从暂存桶读取对象，按文件魔数解码，执行自动旋转、EXIF/GPS 清除和完整重新编码，生成最大 2400px 主图及 960px 缩略图 WebP。任何解码失败或越界资源都标记为失败并清理暂存对象。处理不信任浏览器提供的 MIME、尺寸或扩展名。

至少一张图片达到 `READY` 才允许提交审核。审核前，房东和管理员通过短期签名 GET 查看私有处理图；其他用户不可读取。

### 5.5 审核、发布与紧急下架

管理员人工审核房源和全部媒体。批准时，服务端把已批准处理图复制到公开成品桶，写入公开 CDN 地址，原子更新发布状态与 `Listing.image` 封面。发布操作可安全重试，不得产生重复媒体或半公开响应。

管理员可将已发布房源改为 `SUSPENDED`，必须填写原因并写审计事件。下架后公开查询立即不再返回该房源；公开对象可在短暂缓存清除窗口后删除，避免数据库与 CDN 状态竞态。

### 5.6 前端发布体验

发布表单改为真实文件选择，包含本地预览、逐张进度、失败重试、删除、拖拽或按钮排序、状态提示和草稿恢复。刷新后根据服务器媒体记录恢复状态；本地只保存未完成选择的最小草稿信息，不保存签名 URL。提交审核按钮在至少一张媒体 `READY` 且其他必填字段通过时才启用。

## 6. 第三批：部署、迁移、监控、备份与恢复

### 6.1 构建与环境

固定 Node.js 22 和现有 pnpm 锁文件。增加 Vercel 前端配置、Render Blueprint、API 生产启动命令和集中式环境变量校验。所有秘密只存在于服务商秘密管理中；仓库仅保存完整但无真实值的 `.env.example`。

生产 API 启动时校验数据库、Valkey、Resend、R2、JWT、受信代理、允许源、Sentry 和日志配置。安全关键依赖缺失时拒绝启动。

### 6.2 CI/CD 与数据库迁移

Pull Request 必须运行前后端测试、类型检查、构建、Prisma 校验以及 PostgreSQL 16 空库迁移测试。现有六个迁移文件保持不可变，新增迁移遵循 expand/contract。

`main` 自动部署 staging。生产发布通过 GitHub Environment 人工批准，并将 staging 已验证的同一 Git SHA 分别部署到 Vercel 和 Render。生产数据库只运行 `prisma migrate deploy`；Render pre-deploy 阶段先迁移，再替换 API 实例。禁止生产 `db push`、开发迁移、自动 seed 和 Adminer。

### 6.3 日志、错误监控与告警

API 输出脱敏 JSON 日志，包含请求 ID、版本、路由模板、状态码和耗时。不得记录 Token、Cookie、验证码、完整邮箱、请求正文、上传对象键或签名 URL。前端和 API 的 Sentry release 均绑定 Git SHA。

Better Stack 接收结构化日志并监控首页、`/health`、`/ready`、SSL 和备份心跳。至少配置：

- 连续 3 次不可用；
- 5 分钟内 5xx 数量至少 10 或错误率至少 1%；
- 新的高严重度错误；
- 邮件失败率至少 20%；
- 数据库容量 70% 警告、85% 严重；
- 备份超过 26 小时未成功。

所有严重告警同时通知主联系人和备用联系人，并有明确的责任人与运行手册链接。

### 6.4 备份与恢复

Render PostgreSQL 使用支持 7 天 PITR 的付费层。另建每日任务执行 `pg_dump -Fc`，加密传输到独立私有 R2 备份桶，保留 35 天，并发送成功心跳。备份任务使用只读、最小权限数据库账号和独立 R2 凭据。

目标为 RPO 不超过 10 分钟、RTO 不超过 60 分钟。上线前完成一次 PITR 恢复和一次 R2 异地逻辑备份恢复；逻辑备份只恢复到空数据库。每月执行异地恢复演练，每季度执行 PITR 演练，并保存恢复耗时、数据校验和改进项。

应用回滚优先恢复上一版前端/API。数据库事故进入维护模式，通过 PITR 恢复到新实例；完成迁移状态、关键表数据量、权限与核心冒烟验证后，才切换连接到恢复实例。

## 7. 数据流与组件边界

### 7.1 登录

浏览器生成设备 ID → API 检查受信 IP、邀请资格与多维限流 → 短事务创建 `PENDING` 验证码 → Resend 发送 → API 标为 `SENT` → 用户提交验证码 → API 再次限流并验证哈希 → 创建或登录用户 → 签发会话。

### 7.2 图片发布

房东选择文件 → API 创建媒体记录和预签名 PUT → 浏览器直传私有暂存桶 → 浏览器调用幂等 `finalize` → 工作进程验证、重编码并保存私有成品 → 房东提交审核 → 管理员短期预览并批准 → API 复制到公开桶并发布房源。

### 7.3 运维

Git SHA 通过 CI → 自动部署 staging → 完成真实邮件、媒体和冒烟验证 → 人工批准同 SHA 生产发布 → pre-deploy 迁移 → 零停机替换 API → 外部监控与 Sentry 验证 release → 备份心跳持续检查。

## 8. 错误契约

新增稳定错误码：

- `AUTH_DELIVERY_UNAVAILABLE`；
- `AUTH_RATE_LIMITED`；
- `ADMIN_REAUTH_REQUIRED`；
- `LEGACY_LISTINGS_RETIRED`；
- 媒体上传错误族，包括文件类型、大小、像素、数量、签名过期、对象不匹配、处理失败和状态冲突。

客户端只根据 HTTP 状态与稳定错误码决定交互，不解析服务端错误文案。所有错误响应带请求 ID；内部原因进入脱敏日志和 Sentry，但不暴露给用户。

## 9. 测试与验收门槛

### 第一批

- staging 使用真实 Resend 完成邀请、注册、验证码登录和管理员二次验证；
- 覆盖邮箱、设备、IP、全站限流与 Valkey 故障时失败关闭；
- 验证发送失败保留上一条有效验证码；
- 验证生产环境无法通过 `LOCAL_ADMIN_EMAILS` 提权；
- 验证最后一名管理员保护、30 分钟二次验证和审计不可修改。

### 第二批

- 旧房源接口所有方法均返回 410，应用数据库角色无法写旧表；
- 覆盖越权上传、伪造文件、过期签名、重复 `finalize`、图片上限和错误恢复；
- 验证自动旋转、EXIF/GPS 清除、私有预览、排序、封面和草稿恢复；
- 验证审核发布、公开响应过滤及紧急下架；
- 使用现有数据库快照执行升级，确认房源、用户和审核记录无损。

### 第三批

- 全套 CI、staging 部署、同 SHA 生产晋级和部署冒烟通过；
- 日志脱敏测试证明敏感字段不会落盘或发往外部；
- Sentry release、可用性、阈值告警、邮件失败率和备份心跳均实际触发过；
- PITR 和 R2 异地恢复均满足 RPO/RTO，并有签字记录和可重复运行手册。

任何一项上线门槛失败都阻止生产放量。默认持续保持邀请制内测。

## 10. 实施顺序与依赖

第一批先建立安全身份边界，因为后续上传、审核和运维命令都依赖可信用户与管理员身份。第二批再替换媒体写入与审核链路。第三批最后固化环境、部署、告警与恢复，并用前两批的真实流程完成 staging 和生产演练。

外部前置条件包括：已控制的发信子域名、Resend/Render/Cloudflare/Vercel/Sentry/Better Stack 账号与生产项目、GitHub Environment 审批人、主备告警联系人。缺少外部凭据不阻止本地代码和自动化测试，但会阻止对应 staging 验收和生产放量。
