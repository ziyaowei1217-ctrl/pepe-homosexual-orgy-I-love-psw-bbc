# Marketplace Demo Closure Design

**Date:** 2026-08-14
**Status:** Approved for implementation

## Goal

Turn every renter- and host-facing placeholder in the core marketplace journey into a persistent, demonstrable workflow without processing real money or collecting high-risk identity documents.

The finished journey is:

1. A host publishes a date-bounded listing and uploads its photos.
2. A renter finds listings whose availability fully covers the requested stay.
3. Reciprocal roommate matches can message each other and form one confirmed two-person team.
4. A renter applies alone or with the confirmed team.
5. The listing owner accepts or rejects the application.
6. An accepted applicant completes a clearly labelled simulated deposit payment.
7. The simulated deposit is held, refunded, or released through an auditable state machine.

## Product Boundaries

This release is a demo-quality, backend-persistent workflow. It does not:

- connect to a payment processor or move real funds;
- claim to provide legally regulated escrow;
- collect government ID, bank statements, credit reports, or background-check documents;
- support groups larger than two people;
- add roommate group chat, attachments, presence, typing indicators, message editing, or message recall;
- add automated image moderation or production malware scanning;
- change the retired `HousingListing` API.

Every simulated-money surface must display “演示模式，不会真实扣款” and avoid presenting the feature as real escrow.

## Architecture

PostgreSQL is authoritative for every workflow state. Browser state may provide optimistic presentation but cannot manufacture successful business outcomes. Each mutation is authenticated, authorized against the affected resource, and idempotent where a retry could duplicate a record or state transition.

The work is divided into five bounded backend modules plus focused frontend feature components:

1. **Listing availability** owns the available date interval and collection filtering.
2. **Listing media** owns MinIO-backed direct upload, validation, ordering, cover selection, and removal.
3. **Roommate teams** owns invitations, confirmed two-person membership, leave/dissolve behavior, and its relationship to a deal room.
4. **Applications** owns applicant snapshots, solo/team scope, submission, withdrawal, and owner decisions.
5. **Demo payments** owns simulated payment attempts, held balances, refunds, releases, and an immutable ledger.

The existing roommate-conversation module remains authoritative for direct messages. The current capability gate and stale “unavailable” UI are removed; no second messaging implementation is introduced.

`components/sublet-app.tsx` is already too broad for safe changes across these workflows. Only the affected date filter, media uploader, team controls, application flow, owner review panel, and demo-money panel are extracted. Unrelated UI is left untouched.

## Data Model

### Listing Availability

Add required `availableFrom` and `availableTo` date columns to `Listing`. Existing seeded and migrated records receive explicit safe defaults in the migration/seed path. New or edited listings validate that the end is after the start.

Submitted or approved listings that change either availability date enter a fresh `SUBMITTED` review cycle automatically, because the public offer changed materially. Saving the new dates refreshes `submittedAt` and clears the previous reviewer, review timestamp, and rejection reason; the host does not click Submit a second time.

The collection API accepts `moveIn` and `moveOut` only as a pair. A listing matches when:

```text
availableFrom <= moveIn AND availableTo >= moveOut
```

Invalid, incomplete, or reversed ranges return a structured 400 response rather than silently broadening the search.

### Listing Media

Reuse `ListingMedia` and its storage/review fields. Add the API operations needed to complete its existing lifecycle:

- initialize an upload and return a short-lived presigned MinIO PUT URL;
- finalize an uploaded object after verifying object metadata and magic bytes;
- list the owner’s media for a draft;
- reorder media and choose the first item as cover;
- remove media from an editable draft and delete its object;
- publish only finalized `READY` media when the listing is approved.

The persisted storage lifecycle maps exactly to the product language:

```text
PENDING_UPLOAD (待上传)
  -> UPLOADED_PENDING_VALIDATION (已上传待校验)
  -> READY (可用)
  -> PUBLISHED (已发布)
```

Validation failure moves the item to `FAILED` and stores only a stable `securityErrorCode`; object-store errors, decoder details, filenames, and other internals are never returned to the client. A retry reuses the same media row with a newly generated object key and returns it to `PENDING_UPLOAD`.

Supported formats are JPEG, PNG, and WebP. Limits are 10 MB per image and 12 images per listing. Object keys are generated by the server and never contain the original filename. The application stores only object keys and metadata; public URLs are derived through the media delivery boundary.

Finalization verifies the stored object rather than trusting request metadata: object existence and byte length, magic-byte file type, a SHA-256 checksum computed from the stored bytes, and decodable image dimensions. Image decoding uses a 40-megapixel input-pixel ceiling. The browser may compute the expected SHA-256 value for comparison, but it cannot approve its own upload.

Media may be changed while a listing is `DRAFT` or `REJECTED`. Submitted or approved media are locked. Submission requires at least one MinIO-backed `READY` image, a valid cover, and no remaining `PENDING_UPLOAD`, `UPLOADED_PENDING_VALIDATION`, or `FAILED` images. Any future approved-listing media edit must explicitly move the listing back through review.

Approval changes the listing and all ordered `READY` images to `APPROVED`/`PUBLISHED` in the same transaction. If an approved listing changes dates, its published image records stay locked, but public media delivery also checks the parent listing status and hides the bytes while the listing is back in review.

### Roommate Teams

Add `RoommateTeam`, `RoommateTeamMember`, and `RoommateTeamInvite`.

- An invite is `PENDING`, `ACCEPTED`, `DECLINED`, `CANCELLED`, or `EXPIRED`.
- A team is `ACTIVE` or `DISSOLVED`.
- A team always contains exactly two distinct users.
- An invitation is allowed only when an active reciprocal `RoommateMatch` exists.
- A user may belong to only one active team at a time.
- A user may have multiple pending invitations while they have no active team.
- Accepting an invitation and creating memberships happens in one transaction with concurrency protection; the same transaction cancels every other pending invitation involving either new member.
- Leaving dissolves the team; conversation and application history remain.

An active team may create or attach to a deal room, but `DealRoom` is not the source of truth for team membership.

### Applications

Add `RentalApplication` with a unique active application per listing and applicant scope. It stores:

- listing, listing-owner, and submitting-user relationships;
- `SOLO` or `TEAM` scope and an optional active team relationship;
- immutable applicant/member display snapshots;
- move-in and move-out dates;
- school or occupation;
- income band;
- guarantor status;
- a bounded free-text note;
- status timestamps and owner decision metadata.

Statuses are `DRAFT`, `SUBMITTED`, `ACCEPTED`, `REJECTED`, `WITHDRAWN`, `CANCELLED`, and `COMPLETED`.

A submitted application must fit completely within the current listing availability. Team applications require an active team containing the submitter. Applications never contain sensitive identity or financial documents.

If a team dissolves, its draft applications lose submission eligibility and its submitted applications become `WITHDRAWN` with the system reason `TEAM_DISSOLVED`. An already accepted application remains accepted and must use the normal cancellation flow so payment and ledger state cannot be bypassed.

Only one application per listing may be accepted and unfinished at a time. While it remains accepted, the listing is marked in progress, new submissions are blocked, and other submitted applications remain pending but cannot be accepted. Cancelling it reopens the listing; releasing its held funds completes the listing workflow and permanently closes it to further applications.

Only the listing owner can list and decide applications for that listing. Applicants can read their own applications and withdraw a submitted application before owner acceptance. After acceptance, either the applicant or listing owner may cancel before the agreed move-in date; cancellation records the actor and reason and automatically refunds any held demo funds in the same transaction. Releasing held funds transitions the application to `COMPLETED`.

### Demo Payments And Held Funds

Add `DemoPayment`, `DemoPaymentAttempt`, `DemoHeldFund`, and `DemoLedgerEntry`.

- An accepted application creates or reuses one payment order for exactly one month of listing rent, stored in integer cents.
- Each simulation appends a payment attempt in `SUCCEEDED` or `FAILED` state while the payment order records its current aggregate state.
- The first successful attempt creates one held-fund record in `HELD` state; later success retries return the same records.
- Held funds transition to `REFUNDED` before move-in cancellation or `RELEASED` after both parties confirm move-in on or after the agreed move-in date.
- The renter and listing owner each have one monotonic move-in confirmation timestamp.
- Every balance-affecting transition appends an immutable ledger entry.
- Idempotency keys prevent duplicate payments, refunds, releases, confirmations, and ledger entries.

No card number or payment credential is requested. The demo UI offers deterministic “simulate success” and “simulate failure” actions. Cancellation before move-in closes an unpaid order without manufacturing a refund entry, or atomically refunds a held balance and appends its ledger entry. Post-move-in disputes are outside this demo: held funds remain held until both confirmations arrive.

## API Shape

The existing `/api/v1/listings` collection receives date query parameters, while owner create/update DTOs receive availability fields.

Media routes live below the owned listing:

```text
POST   /listings/:id/media/uploads
POST   /listings/:id/media/:mediaId/finalize
GET    /listings/:id/media
PATCH  /listings/:id/media/order
DELETE /listings/:id/media/:mediaId
```

Team routes are authenticated:

```text
GET    /roommate-teams/current
POST   /roommate-teams/invites
GET    /roommate-teams/invites
POST   /roommate-teams/invites/:id/accept
POST   /roommate-teams/invites/:id/decline
POST   /roommate-teams/invites/:id/cancel
POST   /roommate-teams/current/leave
```

Application routes are authenticated and separated by viewer responsibility:

```text
POST   /applications
GET    /applications/mine
GET    /applications/host-inbox
GET    /applications/:id
POST   /applications/:id/submit
POST   /applications/:id/withdraw
POST   /applications/:id/accept
POST   /applications/:id/reject
POST   /applications/:id/cancel
```

Demo-money routes make their nature explicit:

```text
GET    /demo-payments/by-application/:applicationId
POST   /demo-payments/by-application/:applicationId/simulate-success
POST   /demo-payments/by-application/:applicationId/simulate-failure
POST   /demo-held-funds/:id/confirm-move-in
```

All retryable write routes accept an idempotency key. The server binds each key to the actor, command, resource, and request hash: an exact replay returns the original result, while reuse with different parameters returns a conflict. Authorization uses the authenticated user and server-side resource relationships, never user-supplied ownership fields.

## Frontend Experience

### Search Dates

The existing calendar becomes enabled. Labels use “入住/退租” and duration in days, not hotel-night language. A partial pair is retained in the form but does not filter and prompts the renter to complete both dates. Selecting a valid pair updates the URL search parameters and refetches the server collection. Clearing dates restores the unfiltered collection.

### Roommate Messaging And Teams

Reciprocal matches show an enabled “私信” action that opens the existing durable conversation. Non-mutual states explain what is still required.

The team action reflects server state: invite, pending, accept/decline, active team, or leave team. Both users see the same persisted result after refresh. An active team is available as the application scope and existing deal-room surfaces display the confirmed members.

### Host Media Upload

The publish wizard accepts drag-and-drop or file selection, shows local previews and individual progress, and supports retry, reorder, cover choice, and removal. URL text entry is removed from the primary flow. Failed uploads retain a retry action without pretending the file is saved.

### Applications

The listing detail action opens a short multi-step application panel: scope, dates, profile details, review, submit. Existing profile data is prefilled when safe. The applicant can follow the application status from Trips.

The host receives an application inbox for owned listings and can inspect, accept, or reject a submitted application. Decisions require confirmation and are immediately visible to the applicant.

### Demo Money

Only an accepted application shows the demo payment panel. It repeats the listing, applicant scope, amount, and prominent no-charge disclaimer. Success advances to held funds; failure remains retryable. The held-fund timeline shows renter/host confirmations and the terminal refunded or released state. Cancelling an accepted application before release records a reason and drives the refund; there is no standalone client-side “force refund” command.

## Error Handling And Concurrency

- API errors use stable product codes with safe Chinese messages.
- Validation errors identify the affected field without exposing internals.
- MinIO unavailability leaves media retryable and never creates a false `READY` state.
- State transitions use conditional updates or transactions so stale screens return a conflict response instead of overwriting newer decisions.
- Team acceptance serializes membership creation to prevent two active teams.
- Team acceptance cancels both members' competing pending invitations in the same transaction.
- Submission, review, application decisions, payment, refund, confirmation, release, and ledger mutations are idempotent and transactional.
- UI buttons disable while their command is pending, but reload always recovers from server state.
- No raw storage URL, credential, token, object-store error, or caught database message appears in logs or client responses.

## Testing

Each feature begins with unit/service tests and finishes with public-boundary integration coverage.

Required checks include:

- exact and boundary-inclusive date coverage plus invalid range rejection;
- listing review reset after availability changes;
- media type/size/count validation, finalize failure, retry, ordering, removal, and authorization;
- reciprocal-match requirement, multiple pending invites, competing-invite cancellation, concurrent accept protection, one-active-team rule, and dissolve behavior;
- solo/team application authorization, availability validation, team-dissolution withdrawal, one unfinished accepted application per listing, idempotent submission, owner-only decisions, and terminal-state conflicts;
- simulated success/failure, one payment per accepted application, unpaid cancellation, immutable balanced ledger, idempotent refund/release, move-in-date enforcement, and dual move-in confirmation;
- roommate messaging capability enabled only for a server-confirmed reciprocal conversation;
- frontend tests for refresh recovery, disabled/pending states, safe error copy, and the mandatory demo-money disclaimer;
- a Docker-backed smoke journey using PostgreSQL and MinIO from listing creation through held-fund release.

The release gate remains lint, typecheck, unit/integration tests, production build, Prisma validation, and the new opt-in PostgreSQL/MinIO smoke test.
