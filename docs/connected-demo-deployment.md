### Readiness probe cadence

Production readiness coalesces concurrent requests and caches a completed healthy check for up to 60 seconds per API process, or a failed check for five seconds. A fresh check queries PostgreSQL and probes authentication quotas, message quotas and the realtime Pub/Sub round trip; ordinary host polling and public traffic share that result. Known messaging degradation invalidates a cached success. A healthy response can otherwise reflect a check completed up to 60 seconds earlier; detecting an unknown outage also depends on the next host poll and fresh probe. A cached failure can delay recovery detection for five seconds before a new probe. Each caller still has a 3.5-second response bound, while an unfinished underlying check remains shared until its transport deadline settles it. Development readiness stays fresh on every request. Authentication and message operations continue to enforce their own fail-closed infrastructure checks; a cached readiness result does not authorize an operation. Restarts, failures, application traffic and multiple API processes add provider usage beyond the healthy readiness cadence.

### Optional AI on Netlify

Netlify automatically injects provider credentials at function startup, so an absent operator-supplied Anthropic key alone does not keep AI unavailable on that host. Its [documented environment-variable rules](https://docs.netlify.com/build/ai-gateway/overview/#managing-environment-variables) suppress the Anthropic key/base-URL pair when either is explicitly configured. Set only the official `ANTHROPIC_BASE_URL` above for this project's Functions; without an explicit key the existing assistant stays hidden and its generation routes reject requests. This avoids metered gateway inference consuming shared hosting credits, preserves deliberate use of a genuine provider key later, and leaves other team projects untouched. Verify `/api/assistant` returns `enabled: false` on the deployed website. Do not invoke a model merely to test the disabled state.

### Proxy trust acceptance

[Render's authentication guide](https://render.com/articles/how-to-implement-authentication-and-authorization) uses Express `trust proxy` with a numeric value of `1`. This is a documented starting point, not evidence that this deployment has exactly one visible hop or that the selected address is the final person's IP. [Render's edge-protection guide](https://render.com/articles/how-render-handles-ddos-attacks) describes both Cloudflare and its load balancers; [Express's own guidance](https://expressjs.com/en/guide/behind-proxies/) requires the trust configuration to match the actual paths. Do not switch to unlimited trust or read the leftmost forwarded address directly.

Before calling the setting verified, make a few invalid-token exchange requests from the same controlled source: one without forged forwarding headers, then requests with distinct test `X-Forwarded-For` chains and forged `CF-Connecting-IP`, `True-Client-IP` and `X-Real-IP`. Read only the relevant hashed-IP quota counters in the private distributed store before and after each request. The same source must remain in the same quota bucket. Use fresh test device IDs to isolate that dimension, do not create real accounts, and let the few test quota entries expire normally. Store only pass/fail/count evidence, never raw IP addresses or public debug endpoints. A passing check establishes resistance to these forged headers; determining the actual end-user IP also requires verifying the real proxy chain and shortest ingress path.

### Next 15 authentication transport

The pinned `@neondatabase/auth` 0.7.0-beta generic client and `/server` Fetch toolkit are used through the official framework-adapter interface. The SDK's optional Next peer targets Next 16; this release imports neither `/next` nor `/next/server` and does not upgrade the application. The project's own Next 15 Node route mounts only Google social sign-in, session/token reads, logout and a dedicated callback. It rejects arbitrary provider routes, cross-origin writes, unconfigured hosts, extra redirect targets and oversized JSON. Request bodies are canceled after five seconds.

The callback uses the toolkit's challenge/verifier exchange and preserves individual first-party Secure/HttpOnly cookies, avoiding third-party-cookie dependence in Safari. The temporary `neon_auth_session_verifier` arrives in the callback query and is removed by the immediate redirect after exchange; access/session tokens and return targets are not put in callback URLs. On success it redirects to `/auth/complete`; the UI requests a Neon JWT and exchanges it with the existing Nest API. Client session data is not accepted as proof of identity. [Neon's JWT guide](https://neon.com/docs/auth/guides/plugins/jwt) describes the signed token and JWKS contract.

The current toolkit does not expose an abort signal or fetch-timeout setting for its provider transport. The route declares `maxDuration=15` for compatible platforms, but this is **not a verified Netlify timeout**. Netlify documents a fixed 60-second synchronous function limit. Provider outages can therefore consume an invocation up to that platform limit; there is no early-response timeout that leaves a detached OAuth write running. Recheck the actual adapter/function settings when deploying. See [Netlify function limits](https://docs.netlify.com/build/functions/configuration/) and [the SDK's official adapter guide](https://github.com/neondatabase/neon-js/blob/main/packages/auth/BUILDING-AN-ADAPTER.md).

### What worked with Netlify CLI 27.10.2 (October 24, 2026)

Observed while deploying commit 1a8d173 (draft 6adce135aadb25024b0e4726):

- A local CLI build receives a masked placeholder for marked-secret variables and overrides values from the shell, so `tools/netlify-build-config.mjs` always rejects the cookie secret in a local `netlify build` or `netlify deploy --build`.
- `netlify env:set` refuses to change an existing variable when both context and scope are given. `deploy --no-build` refuses `--context`.
- A `deploy --no-build` upload with no env flags produced functions with no settings: auth returned 503 `AUTH_PROVIDER_UNAVAILABLE` and `/api/assistant` reported `enabled:true` through the AI Gateway because `ANTHROPIC_BASE_URL` was missing. Never publish such a deploy.
- `deploy --env` and `--secret-env` apply to that deploy's functions only, not to the build.

The working sequence:

1. Run `netlify build --offline` at the reviewed commit. Export only the non-secret production values (`env:get --context production`) into the operator shell, and give the preflight a throwaway cookie value. Confirm the throwaway value appears in 0 output files and logs.
2. Run `netlify deploy --no-build` without `--context` or `--prod`. Pass `--env NAME="$VAR"` for the six non-secret variables (`NEXT_PUBLIC_API_BASE_URL`, `NEXT_PUBLIC_AUTH_PROVIDER`, `NEXT_PUBLIC_MEDIA_UPLOAD_ORIGIN`, `ANTHROPIC_BASE_URL`, `NEON_AUTH_APP_ORIGIN`, `NEON_AUTH_BASE_URL`) and `--secret-env "NEON_AUTH_COOKIE_SECRET=$S"`. `$S` is a fresh random 48-character value held only in a shell variable and unset afterwards. Because stored secrets cannot be read back, this rotates the cookie secret for that deploy, which signs out existing sessions when it is published.
3. On the draft, check that `GET /api/assistant` returns `{"enabled":false}` first, and that a POST to `/api/auth/email-otp/send-verification-otp` from the draft origin returns 403 `AUTH_ORIGIN_REJECTED`, which shows the proxy has its settings.
4. Publish with `netlify api restoreSiteDeploy` (or "Publish deploy" in the dashboard). Record the previous published deploy ID first for rollback. Claude Code's auto-mode permission check on the operator Mac treats this step as a production deploy and blocks it, so the owner publishes.

The immutable candidate has a different browser origin from the stable website. Production `WEB_ORIGIN` is a single exact HTTPS origin: a stable-only API will correctly reject candidate-origin authentication and sockets. Use a staging API configured for the exact candidate origin, or deliberately configure that API for the exact candidate during its review and restore the stable origin before publication. Recheck the stable site's authentication and WebSocket connection after this change. Do not use `*`, an unvalidated comma-separated value or a broadly permitted Netlify suffix to make preview tests pass.

If the provider and function configuration deliberately authorize only the stable origin, a candidate's expected origin rejection does not establish working OAuth. After CI, artifact and anonymous HTTP checks pass, an operator may promote that exact artifact for controlled acceptance at the stable origin, with the previous deploy ID retained for immediate rollback. Perform actual login and the shared-account/core journeys there before declaring the release ready; restore the previous deploy if authentication or a required journey fails. Record these as live acceptance results, not as previously verified preview behavior. Do not weaken origin guards for this process.

Do not publish an apparently interactive frontend while its real API or selected identity provider is missing. Keep the existing live release available until the connected candidate has actually passed its checks.
